# Sulla Files — Architecture and Agent Reference

This is the detailed reference for the Sulla Files system. For quick agent guidance,
see the prompt-injected Files block. For working rules, see [files-harness.md](files-harness.md).

## How agents use Files

Sulla Files is mounted at `/mnt/sulla-files` via FUSE. Agents use **normal file
tools** — ls, cat, edit, write, mv, cp, mkdir, rm, Python file I/O — on the mount.
No special Sulla CLI tools are needed for reading or writing files. The Files
service intercepts every operation through the FUSE adapter and handles versioning,
merge, audit, and identity automatically.

### What happens on every write

1. The FUSE adapter sends the write to the Files service with the agent's identity
   (`X-Sulla-Actor: <agentId>:<jobId>`).
2. The Files service creates a new **version** of the file. Agent writes are drafts;
   the published version does not change until a human approves.
3. If the write is based on a stale version (another agent or the human changed the
   file since it was read), the Files service uses **Automerge** to merge the
   changes for UTF-8 text files. The merge is server-side; the agent sees no error.
   Binary files (images, PDFs) are saved as whole-file replacement versions —
   no merge attempted.
4. The write is recorded in the **audit log** with the agent's identity, timestamp,
   file path, and action.

### Temporary work

Use `/tmp/<your job id>/` for scratch work. Move anything worth keeping into
`/mnt/sulla-files` when done. There is no scratch collection system.

### Folder metadata: `_folder-metadata.yaml`

Every folder on the mount has a `_folder-metadata.yaml` file. It is generated by
the Files service and visible to agents and humans. It describes the folder's
purpose and lists metadata for its files.

```yaml
# _folder-metadata.yaml — edit this file to update folder and file metadata.
# Changes are saved back to the Files database automatically.
folder:
  description: "Client contracts and agreements"
  naming_hint: "<client-name>-<document-type>-<date>.pdf"
files:
  contract-acme-2026-03.pdf:
    description: "Acme Corp service agreement, March 2026"
    tags: [contract, acme, active]
```

**When you create a folder**, fill in the `description` field so future agents know
what belongs there. Read existing `_folder-metadata.yaml` files to understand a
folder before writing to it.

The YAML file is the agent-friendly surface. Underneath, the metadata is stored in
Postgres and also available as extended attributes (`user.sulla.*`) on the FUSE
mount.

Inside git repositories (detected by the presence of a `.git` directory), the
`_folder-metadata.yaml` file is not generated to avoid polluting the repo.

### Remaining CLI tools

These Sulla CLI tools are still available:

| Tool | Purpose |
|------|---------|
| `sulla files/search` | Hybrid search over files by meaning |
| `sulla files/history` | List every version of a file (pass `--path` for mount paths) |
| `sulla files/restore` | Restore a previous version (pass `--path` for mount paths) |
| `sulla files/link` | Create a public share link |
| `sulla files/shared` | List public share links |
| `sulla files/revoke_link` | Revoke a share link |
| `sulla files/where` | Find the best folder for a new file |
| `sulla files/create_folder` | Create a folder with a description |
| `sulla files/versions` | List versions with draft/published state |
| `sulla files/request_publish` | Ask a human to publish a draft |

The retired tools (`files/put`, `files/get`, `files/list`, `files/promote`) no
longer exist. Use normal file tools on the mount instead.

### Per-agent identity

Every write through the FUSE mount carries the writing agent's identity. This
enables:
- **Audit trail**: who changed what, when
- **Per-agent permissions** (planned): restrict which agents can write to which paths
- **Conflict attribution**: when Automerge merges concurrent edits, both authors
  are recorded

The identity comes from the `X-Sulla-Actor` header, which the FUSE adapter sets
from the agent's authenticated context. Agents do not need to set this manually.

## Authority and custody

The Files service owns collection keys, encrypted storage, file metadata and versions, sharing, indexing, migration, recovery decisions, and its ready/locked state. Desktop, chat, agents and other integrations call its authenticated API.

### File Manager tree and FUSE mount

The File Manager namespace is the path authority. The FUSE adapter exposes
that same namespace at `/mnt/sulla-files`: the default Files collection maps to
the mount root, while non-default collections retain their
`collections.explorer_path` mapping. A path such as
`Clients/Acme/contract.pdf` in File Manager is the same path at
`/mnt/sulla-files/Clients/Acme/contract.pdf`.

The mount supports reads, writes, empty-file creation, `mkdir`, file and folder
rename/move (including cross-collection moves), `unlink`, and empty
`rmdir`, plus appends (`>>`) and exclusive create (`O_EXCL`). Mutations call the
authenticated Files service. Deletes enter Files history/Trash rather than
bypassing it. The adapter shares one tree snapshot across all lookups for up to
one second, so File Manager changes show up in the mount within about a second.

Paths are canonical relative POSIX paths. Absolute paths, empty components,
`.`/`..`, backslashes, protected wallet/vault names, symlink traversal, and raw
host paths are rejected. Crypto-wallet data is never admitted to the tree.

### Agent access and system areas

Agents can read and write non-system files through
FUSE. Every agent write creates a draft version (see
[Versions, drafts, and approval](#versions-drafts-and-approval)).

The Files-owned system collections are:

- `Sulla`: `Docs`, `Use Cases/{skills,workflows,agents,functions,recipes}`,
  `Projects`, and `Identity`.
- `Logs`: hidden behind **Trash → More**, with `audit/files`, `audit/vault`
  and `app` folders.
- `Training Data`: hidden behind **Trash → More**.

Logs and Training Data are read-only to callers; only services write them.
Audit files are append-only JSONL at `Logs/audit/files/<file-id>.jsonl` and
`Logs/audit/vault/<secret-id>.jsonl`.

Use Cases folders are the file authority; database definitions are runtime
indexes. See [files-harness.md](files-harness.md) for working rules and
[files-first.md](files-first.md) for the layout.

## Desktop bootstrap

The native bootstrap helper runs in an isolated process before the ordinary Desktop module graph loads. It unwraps OS-protected Files material and sends it directly to the authenticated Files service. The Desktop parent receives status only. The Files master and bootstrap identity are distinct from Vault secrets.

The handoff must authenticate both ends, bind the destination and caller, expire quickly, reject replay, and encrypt the key payload. Certificate verification must remain enabled with the provisioned Files identity. A local API token alone is not sufficient protection for transporting a plaintext master key.

Files decides whether an existing master is usable, whether an empty store may be initialized, or whether complete authorized recovery is available. Missing OS material with existing encrypted data must never trigger an unconditional replacement key. Initialization failures must remain distinguishable from verifier rejection; a failed database query or ownership migration is not a reason to replace a master key.

Lock invalidates outstanding bootstrap work and clears live keys. A late asynchronous startup completion must not make a locked service ready again.

## Collection envelopes and migration

Files generates collection data and deduplication keys and persists authenticated envelopes. The master protects those envelopes. Vault may authenticate a principal and hold authorized recovery envelopes, while Files owns their use in file lifecycle operations.

Existing content ciphertext and working collection keys must survive migration. Where a supported historical scheme derived collection keys from a signing secret, migration wraps those same keys without changing their value. Unknown or inconsistent historical state must remain preserved and produce a bounded error. Recovery requires a complete, context-verified key set before committing replacement envelopes. If the canonical OS master is missing and only historical legacy archives remain, automatic bootstrap refuses fresh-key creation. Preserve the archives and restore the original protected master or use an explicitly supported recovery procedure; do not delete key state to make startup pass.

Desktop principal adoption is limited to legacy desktop-user collections. Other collection owners and recovery bundles remain unchanged. Share-link owner changes are limited to the collections actually adopted.

Server deployments use the same Files envelope keyring and file-management core. Their master provisioning mechanism may differ from the native OS helper, but must not turn authentication signing credentials into new content-encryption keys.

## Verification and operation

Use synthetic collections and isolated databases to verify envelope preservation, principal isolation, invalid key rejection, replay and expiry, lock/startup races, restart persistence, and migration rollback. Use nonsecret status for live diagnosis. Never print key material, transport credentials, decrypted file contents, or live wallet data.

Rebuild both the Files service and Desktop when their bootstrap contract changes. Preserve the previous deployment and encrypted state until the new pair has passed acceptance. Record the exact source and image revisions; a merged change alone does not prove that the running application uses it.

### Versions, drafts, and approval

Agent identities (including agent jobs, capabilities, and the Files FUSE adapter)
always write a new `draft` version. The published version remains unchanged until
a human approves publication. Agents read the latest version (including drafts)
through normal file tools on the mount, and can list versions with
`sulla files/versions`. To request publication, use `sulla files/request_publish`;
agents cannot publish directly. That request returns immediately and creates a
card in Decide. The Desktop main process performs the eventual publish as the
human identity and reports the outcome to the requesting chat.

The File Manager shows published content to humans, marks files with an unpublished
draft as **Draft pending**, and lists each version as Draft, Published, or
Superseded. A record lock or an active retention policy is enforced by the Files
service for every caller, including agents and FUSE. New versions and deletes of
a locked or retained file fail with HTTP 423 `FILE_LOCKED`. FUSE reports that as
`EROFS`. Other HTTP 409 conflicts (for example, a checkout held by someone else)
report as `EPERM`.

## Editing alongside a human

Agents can edit text files through the Files mount or content API while someone
has them open in the Desktop document editor. The Files service merges these
writes into the same live Automerge document and streams changes to connected
editors. No special agent-side sync code is needed. Live sessions persist a new
version after about two seconds without changes and flush when the last peer
leaves. Older servers and the browser Files UI retain version-checked saving.
