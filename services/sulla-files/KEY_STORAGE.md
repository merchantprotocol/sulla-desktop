# Files key storage

Desktop Files starts locked. Electron supplies a 32-byte master key through the authenticated local unlock endpoint after retrieving it from OS-protected storage. The service never accepts a master key from environment variables, command arguments, compose configuration, or a plaintext file. Restarting the container clears its memory and requires another Desktop unlock.

The database stores an authenticated master-key verifier and wrapped collection keys. Unlock runs a transaction: existing collections retain their original data/deduplication keys, now wrapped by the independent master; newly created Desktop collections receive random keys. A wrong master or malformed wrapped key fails closed. Losing the OS-protected master prevents unlocking; generating a replacement does not repair existing ciphertext.

Legacy collections are marked `legacy-signing-v1`. Migration preserves content and does **not** rotate those historically signing-derived data keys. Someone with the old signing secret can still derive those historical keys. Removing that exposure requires a separate, data-safe content-key rotation. Standalone server mode retains its existing signing-derived protocol; this is not a Desktop fallback. Sync continues for existing migrated legacy collections. Random or unknown collection keys fail closed with an explicit secure-key-exchange error; the current peer protocol cannot exchange those keys.

The retired in-process runtime stored random collection keys behind `~/sulla/files/master.key` and ciphertext below `~/sulla/files/chunks`. Startup classifies that layout from filesystem metadata and database markers before keyring unlock; it never opens chunk contents. The exact root-level `chunks/<collection UUID>/<bucket>/<chunk hash>` shape remains containment evidence even when the old master was already archived/quarantined or the database has no matching collection row. A normal user folder named `chunks` without that shape is not contained. The subtree and any already-indexed watcher records are excluded from ingestion, listing, search, preview, and sharing while records and ciphertext remain untouched.

After the service confirms preflight, Desktop separately places any remaining plaintext legacy master under OS `safeStorage`, verifies the durable archive byte-for-byte after decryption, and only then retires the plaintext source. Archive, verification, metadata, or durability errors preserve the source and keep Files locked. Native key creation never runs while secure import is required.

`files_legacy_preflight.state='secure-import-required'` is deliberately sticky. The scanner and ordinary unlock path cannot clear it. The authorized recovery importer is the explicit completion seam: only after it verifies secure custody and installs authenticated keys for every external collection may it transactionally clear the containment state and protected watcher records. Recovery failure must leave the state, records, and ciphertext unchanged.
Random collections can enroll an opaque recovery bundle through `FilesKeyBundleRecovery`. Enrollment derives the principal, key version, and epoch from the authoritative collection/key rows; callers supply only the collection id. The immutable local envelope is persisted before idempotent Vault registration, so retries and concurrent randomized candidates always converge on the stored winner. A random bundle key is X25519-sealed to the Vault custody recipient; the data and deduplication keys are XChaCha-encrypted with associated data binding the collection, principal, key version, epoch, and envelope purpose. Files persists only that opaque envelope. Recovery asks Vault to authorize the principal/collection/epoch and rewrap the bundle to a one-shot device public key. Files validates the returned context and atomically wraps every recovered collection key under the replacement OS-protected master. Missing bundles, unauthorized principals, moved envelopes, tampering, stale epochs, incomplete collection sets, and legacy keys all fail before local key rows change.

The current replacement-master operation supports one owner principal across every native random-key collection in the local database. ACL sharing does not create another local custody principal. A database containing collections owned by multiple principals fails before any authority request or local rewrap; multi-principal recovery needs an explicit all-principals authorization design rather than a partial key-count shortcut.

The Vault authority adapter is deliberately an explicit interface. Device recovery must remain disabled until Vault implements `custodyRecipient(context)`, idempotent `registerBundle(bundle)`, and `authorizeDeviceRecovery({ context, devicePublicKey })` against its organization membership and collection custody state. Vault must resolve its own registered envelope by the exact context rather than trust an envelope supplied by Files. The Files service does not accept an authority private key, a plaintext exported master, or a caller assertion as authorization.

Files does not recreate the retired plaintext `master.key`. Historical indexed master-key files and their chunks receive persistent deny markers, including after a rename. Ingestion, preview, share relay, search, backup and restore reject or exclude this reserved path as defense in depth. Existing external copies or backups are not automatically erased. The current tar backup still does not capture the Postgres metadata/key-bundle graph and is not a complete restore artifact; coherent database snapshot and chunk-manifest staging remains required before backup can be described as recoverable.

The local unlock API returns success only after initialization. File APIs stay unavailable while locked. Lock drains background work before clearing the master and cached collection-key buffers. Immutable runtime/HTTP strings cannot be reliably scrubbed by JavaScript; no key is intentionally written to disk or logs.
